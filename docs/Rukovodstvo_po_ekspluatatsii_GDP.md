## 1. Цель

Настоящее руководство устанавливает единый порядок эксплуатации графической утилиты
резервного копирования MySQL (далее — Утилита): создание резервных копий,
автоматическое копирование по расписанию, восстановление данных, контроль журналов,
а также требования к целостности данных в соответствии с GDP и принципами GxP.

Цели применения:
- гарантировать возможность восстановления баз данных после сбоев;
- обеспечить прослеживаемость всех операций (audit trail);
- исключить несанкционированный доступ и потерю данных.

## 2. Область применения

Документ обязателен для всего персонала, работающего с Утилитой:
операторов, системных администраторов, ответственных за качество данных лиц.
Распространяется на все серверы MySQL/MariaDB, включённые в область резервного
копирования согласно перечню [перечень систем — указать].

Документ НЕ распространяется на:
- резервное копирование на уровне виртуальных машин / СХД (регулируется отдельными СОП);
- разработку и модификацию исходного кода Утилиты.

## 6. Общие сведения о системе

6.1. Назначение Утилиты: автоматизация создания резервных копий и восстановления
баз данных MySQL/MariaDB через графический интерфейс.
6.2. Состав: исполняемый модуль `MySqlBackupUtility.exe` (WPF, .NET 8, self-contained);
внешние зависимости — клиентские утилиты `mysqldump.exe` и `mysql.exe`
(поставляются в составе MariaDB/MySQL Client, в Утилиту не входят).
6.3. Хранение настроек: локальная база SQLite `%AppData%\MySqlBackupUtility\app.db`
(профили подключений, задачи, архив копий, журнал операций). Пароли — только в
шифрованном виде (DPAPI текущего пользователя Windows).
6.4. Файловый журнал: `%AppData%\MySqlBackupUtility\logs\app-ГГГГММДД.log`.
6.5. Ограничение версии 0.1.0: планировщик встроенный — автоматический запуск задач
выполняется, только пока Утилита запущена (включая свёрнутое состояние в системном трее).
Требование непрерывности вне сеанса пользователя обеспечивается средствами ОС
(см. п. 9.3.6).

## 7. Требования к окружению и установка

7.1. ОС: Windows 10/11, 64-bit. Права для установки MSI: администратор.
.NET устанавливать НЕ требуется (self-contained поставка).
7.2. На компьютере должны быть доступны `mysqldump.exe` и `mysql.exe`:
проверить можно на вкладке «Настройки» (статус утилит) либо командой
`where mysqldump; where mysql` в PowerShell.
7.3. Установка:
  1. Скопировать `MySqlBackupUtility-0.1.0-win-x64.msi` на компьютер.
  2. Запустить двойным кликом, подтвердить запрос UAC.
  3. Проверки приёмки: каталог `C:\Program Files\MySqlBackupUtility\` содержит
     `MySqlBackupUtility.exe`; ярлыки созданы на рабочем столе и в меню «Пуск»
     → «MySQL Backup Utility»; запись присутствует в «Установке и удалении программ».
  4. Первый запуск: вкладка «Настройки» → «Авто-поиск» → «Сохранить пути»
     (при необходимости указать пути вручную, напр.
     `C:\Program Files\MariaDB 12.2\bin\mysqldump.exe`).
7.4. Удаление выполняется штатно через «Установку и удаление программ».
Настройки пользователя в `%AppData%` при этом сохраняются.
7.5. Часы ОС должны быть синхронизированы (доменный NTP): метки времени бэкапов,
журналов и расписаний зависят от системного времени (см. п. 10).

## 8. Управление доступом

8.1. Доступ к Утилите определяется учётной записью Windows пользователя;
отдельных логинов Утилита не ведёт — все действия связываются с сеансом ОС.
8.2. Учётные записи MySQL, используемые в подключениях, создаются по принципу
минимальных привилегий: для бэкапа — `SELECT, SHOW VIEW, TRIGGER, LOCK TABLES`;
для восстановления — полные права на целевую БД.
8.3. Пароли MySQL вводятся один раз при создании подключения и хранятся только
в DPAPI-шифрованном виде; передача пароля внешним утилитам выполняется через
переменную окружения `MYSQL_PWD`, а не через командную строку.
8.4. При увольнении/переводе сотрудника администратор проверяет актуальность
подключений и при необходимости обновляет учётные данные.
8.5. Запрещается: хранить пароли в открытом виде, передавать файлы `app.db`
между пользователями/ПК (DPAPI другого пользователя их не расшифрует —
пароли вводятся заново), отключать audit trail.

## 9. Порядок работы

### 9.1. Управление подключениями

9.1.1. Создать подключение: вкладка «Подключения» → «Новое» → заполнить
Имя / Хост / Порт (по умолчанию 3306) / Пользователь / Пароль; при необходимости —
«Использовать SSL/TLS».
9.1.2. Нажать «Проверить соединение». Ожидаемый результат: сообщение
`OK. Сервер: <хост>:<порт>, версия ...` и зелёный индикатор в строке статуса.
При ошибке — зафиксировать текст ошибки и действовать по Приложению Б.
9.1.3. Нажать «Обновить список БД», отметить галочками базы, подлежащие копированию
(«Выбрать все» = все базы, включая будущие; системные БД скрыты).
Выбор отображается в поле «Базы для бэкапа»: `*` либо имена через запятую.
9.1.4. Нажать «Сохранить». Подключение появляется в списке слева и становится
доступным для задач.
9.1.5. Редактирование/удаление выполняются выделением подключения и кнопками
«Сохранить» / «Удалить» (удаление требует подтверждения; связанные задачи удаляются).

### 9.2. Создание резервной копии вручную

9.2.1. Вкладка «Главная» → «Новая задача» → выбрать «Подключение».
9.2.2. Поле «База данных» допускается оставить пустым — используется выбор
из подключения (п. 9.1.3). Допускается указать явно: одно имя (`lora_gate`),
несколько через запятую (`shop,blog`) или `*` (все пользовательские базы).
9.2.3. Указать папку хранения, периодичность (обязательно выбрать значение),
время/параметры расписания, лимиты хранения, признак «Включена».
9.2.4. Нажать «Сохранить задачу». Задача появляется в таблице со статусом
и временем следующего запуска.
9.2.5. Выделить задачу → «Создать бэкап сейчас». Ожидаемый результат:
файл `[ИмяБД]_[ГГГГММДД]_[ЧЧММСС].sql.gz` в папке, запись во вкладке «Архивы»,
запись уровня OK в «Логах», зелёный индикатор.
9.2.6. При статусе ERROR: зафиксировать сообщение из «Логов» и действовать
по разделу 12. До выяснения причины задача считается невыполненной.

### 9.3. Автоматическое копирование по расписанию

9.3.1. Параметры расписания задачи:
- Daily — ежедневно в указанное время (ЧЧ:ММ);
- Weekly — дни недели цифрами через запятую (0 = воскресенье … 6 = суббота), напр. `1,2,3,4,5`;
- Monthly — число месяца (1–28) в указанное время;
- Interval — каждые N минут (минимум 5).
9.3.2. Политика хранения «Хранить копий / дней» (напр. 7/7): сверхлимитные копии
удаляются автоматически (файл и запись). Значение `0` — без ограничения.
9.3.3. Глобальный флажок «Планировщик вкл» (тулбар) и пункт трея
«Поставить на паузу» / «Продолжить» разрешают/запрещают автозапуск всех задач.
9.3.4. Проверка работы расписания: колонки «Статус» (OK/ERROR) и «След. запуск»;
ежедневный контроль — обязанность администратора (п. 11).
9.3.5. Закрытие окна сворачивает Утилиту в трей (если включено в «Настройках»);
планировщик при этом продолжает работать. Полный выход — только через меню трея
→ «Выход» (после выхода автозапуск НЕ выполняется).
9.3.6. Для выполнения вне сеанса пользователя зарегистрировать запуск Утилиты
в системном планировщике заданий Windows (`taskschd.msc`) [параметры — по СОП
организации]. Факт регистрации фиксируется в журнале изменений системы.

### 9.4. Контроль резервных копий (верификация)

9.4.1. После каждого бэкапа (ручного — сразу, автоматического — при ежедневной
проверке) убедиться: файл существует, размер больше нуля и правдоподобен
(сопоставим с предыдущими копиями той же БД), запись есть во вкладке «Архивы».
9.4.2. Не реже [1 раза в квартал — указать] выполнять тестовое восстановление
копии в отдельную тестовую БД (п. 9.5) с проверкой целостности (число таблиц /
контрольные запросы) и записью результата в журнал (Приложение А).
9.4.3. Копия, не прошедшая верификацию, считается недействительной: задача
переводится на особый контроль, оформляется отклонение (раздел 12).

### 9.5. Восстановление базы данных

9.5.1. Восстановление в продуктивной среде выполняется только с одобрения
ответственного лица (п. 5) и после фиксации текущего состояния (по возможности —
свежий бэкап перезаписываемой БД).
9.5.2. Вкладка «Архивы» → выделить архив → «Восстановить...».
Целевая БД подставляется из задачи; для многобазовых задач имя уточняется
в диалоге (по умолчанию — первая из списка).
9.5.3. Подтвердить предупреждение о перезаписи данных целевой БД.
Ход операции отображается в строке статуса; итог — в «Логах» и всплывающим сообщением.
9.5.4. «Восстановить из файла...» — произвольный `.sql` / `.sql.gz` / `.zip`
(используется первое подключение списка; целевую БД ввести вручную).
9.5.5. После восстановления выполнить проверки целостности (п. 9.4.2) и внести
запись в журнал (Приложение А).

### 9.6. Архивы: просмотр, удаление, папка

Вкладка «Архивы»: «Обновить», «Удалить» (удаляет файл и запись, требует подтверждения),
«Открыть папку». Ручное удаление файлов в обход Утилиты запрещено (нарушает
соответствие записей и файлов); удаление — только через интерфейс или ротацией.

### 9.7. Журналы (audit trail)

9.7.1. Вкладка «Логи» → «Обновить»: время (UTC), уровень (INFO/OK/ERROR), задача,
сообщение, размер, длительность. Дублирующий файловый журнал —
`%AppData%\MySqlBackupUtility\logs\app-ГГГГММДД.log`.
9.7.2. Журнал доступен только для чтения (интерфейс не предоставляет редактирования
или удаления записей) — это обеспечивает неизменность audit trail.
9.7.3. Ошибки уровня ERROR разбираются в день обнаружения (раздел 12).

## 10. Целостность данных (ALCOA+)

Применение принципов в Утилите версии 0.1.0:

| Принцип | Реализация |
|---|---|
| Attributable (принадлежность) | Каждая запись журнала содержит задачу и метку времени; действия выполняются в именованном сеансе Windows |
| Legible (читаемость) | Имена файлов по шаблону; сообщения журналов на естественном языке; файловый лог в открытом текстовом формате |
| Contemporaneous (своевременность) | Записи создаются в момент операции (старт/итог), метки — по системным часам (требуется NTP, п. 7.5) |
| Original (оригинальность) | Дамп — прямой вывод `mysqldump`; сжатие без потерь (gzip); исходные файлы не модифицируются после создания |
| Accurate (точность) | Потоковая запись без промежуточных преобразований; размер и длительность фиксируются в журнале |
| Complete (полнота) | Фиксируются и успехи, и ошибки; ротация удаляет только сверхлимитные копии |
| Consistent (непротиворечивость) | Записи SQLite и файловый лог ведутся синхронно; «Архивы» соответствуют файлам |
| Enduring (сохраняемость) | Копии + журналы хранятся per политике хранения; удаление — только ротацией/подтверждённым действием |
| Available (доступность) | Просмотр через интерфейс; файлы — через «Открыть папку»; резервные копии проверяются восстановлением (п. 9.4.2) |

Известное ограничение версии 0.1.0: электронные подписи операций не предусмотрены;
подтверждение критичных действий (восстановление в продуктивной среде, удаление)
оформляется подписью в бумажном/электронном журнале (Приложение А).

## 11. Периодический пересмотр

11.1. Ежедневно (администратор): статусы задач, записи ERROR за сутки, наличие
свежих файлов копий.
11.2. Еженедельно: соответствие записей «Архивов» файлам; свободное место;
корректность следующих запусков.
11.3. Ежеквартально [указать]: тестовое восстановление (п. 9.4.2); проверка
актуальности подключений и учётных данных; пересмотр политик хранения.
11.4. Результаты фиксируются в журнале (Приложение А) и предъявляются
при проверках/аудитах.

## 12. Отклонения и корректирующие действия

12.1. Отклонением считается: статус ERROR задачи; отсутствие ожидаемой копии;
неуспешная верификация/восстановление; расхождение записей и файлов;
подозрение на компрометацию данных.
12.2. Порядок действий:
  1. Зафиксировать: дата/время, задача, текст ошибки из «Логов», скриншот при необходимости.
  2. Оценить влияние на данные/доступность (критично для продуктивных БД).
  3. Уведомить администратора, при влиянии на качество — ответственное лицо.
  4. Устранить причину (типовые — Приложение Б), перезапустить задачу, убедиться в OK.
  5. Если причина системная/повторяющаяся — оформить CAPA по СОП организации [указать код].
12.3. До закрытия отклонения связанные данные считаются недостоверными
для принятия решений по качеству (отметить в журнале).

## 13. Управление изменениями

13.1. Обновление Утилиты (новый MSI) выполняется администратором: установка поверх
(MajorUpgrade сохраняет данные `%AppData%`); после обновления — smoke-проверка:
запуск, «Проверить соединение», ручной бэкап тестовой задачи, чтение «Логов».
13.2. Изменение расписаний, политик хранения, перечня БД, мест хранения —
только администратором с записью (дата, что изменено, кем, основание).
13.3. Изменение настоящего руководства — через историю изменений и
переутверждение (лист согласования), с ознакомлением персонала.
